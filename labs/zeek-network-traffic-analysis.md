# Zeek — Network Traffic Analysis and Detection

Hands-on learning notes from the [TryHackMe Zeek room](https://tryhackme.com/room/zeekbro).

## Objective

I practised analysing PCAPs with Zeek, querying network logs, writing basic signatures, running event-driven scripts and using file analysis, intelligence and community packages. This write-up combines observed lab results with simple examples explaining the investigation workflow.

## Understanding the workflow

A **PCAP** is a recording of network packets. Zeek interprets that traffic and produces structured logs. A **signature** looks for a defined pattern; a **script** can respond to events, extract fields, maintain counters and correlate activity.

| Log | Investigation purpose |
|---|---|
| `conn.log` | Endpoints, ports, duration and traffic counters |
| `dns.log` | DNS queries and responses |
| `dhcp.log` | Observed DHCP hostnames and network settings |
| `http.log` | HTTP hosts, requested paths and responses |
| `files.log` | File metadata, hashes and extraction details |
| `signatures.log` | Recorded signature matches |
| `notice.log` | Notices generated by detection policies |
| `intel.log` | Matches against supplied intelligence indicators |

```bash
zeek -C -r sample.pcap
```

`-r` reads the capture; `-C` skips checksum validation. Logs are written to the working directory. I learned to verify the directory before running commands: `cd` changes directories, while PCAPs are files to analyse.

## Log analysis with the CLI

```bash
# Unique DNS queries
cat dns.log | zeek-cut query | sort -u | wc -l

# Longest connection duration, in seconds
cat conn.log | zeek-cut duration | sort -nr | head -n 1

# Sent and received packets for connections using source port 38706
cat conn.log | zeek-cut id.orig_p orig_pkts resp_pkts |
  awk '$1 == 38706 {total += $2 + $3} END {print total+0}'
```

Each pipe passes output to the next command. `zeek-cut` selects named fields; `sort -u` removes duplicates; `wc -l` counts rows. In the packet query, `$1` is the source port and `$2` and `$3` are packet counts, not byte counts.

## FTP signatures and interpreting detections

I completed a signature file containing two rules:

```zeek
signature ftp-username {
    ip-proto == tcp
    ftp /.*USER.*/
    event "FTP Username Input Found!"
}

signature ftp-brute {
    ip-proto == tcp
    payload /.*530.*/
    event "FTP Brute-force Attempt!"
}
```

```bash
zeek -C -r ftp.pcap -s ftp-bruteforce.sig
```

The first rule matches FTP username commands. The second searches for `530` in the payload; in the lab this appeared in failed-login responses. The `.*` pattern means zero or more arbitrary characters.

**Illustrative exchange:**

```text
Client: USER admin
Server: 331 Password required
Client: PASS example
Server: 530 Login incorrect
```

This shows a failed login. One failure does not establish brute force. Repeated failures, timing, source IPs and targeted accounts provide the context needed for investigation. The rule's alert message is a label, not proof of an attack.

### Counting the right thing

| Question | What to count |
|---|---|
| Different messages | Distinct `msg` values |
| Connections represented in notices | Distinct `uid` values |
| Total hits of a signature | Matching records, including repetitions |

For example, if connection A generates a username notice and a failure notice, that is **two notice records but one connection UID**.

```bash
# Unique connection UIDs represented in notices
cat notice.log | zeek-cut uid | sort | uniq | wc -l

# Total ftp-brute signature matches
cat signatures.log | zeek-cut sig_id | grep -x 'ftp-brute' | wc -l
```

In a separate script-and-signature exercise, I observed **1,401 signature hits**, including **731 detections of the exact username `administrator`**.

## Event-driven scripts and DHCP

I learned that `zeek_init` runs at startup, `zeek_done` at shutdown and `new_connection` when a new connection is identified. The connection script reported **87 new connections** in its exercise capture. Fields printed at connection creation may not yet contain final duration or counters.

DHCP exchanges provide network configuration. A typical exchange is Discover, Offer, Request and ACK (DORA). Zeek observes the exchange; it does not assign addresses.

```bash
cat dhcp.log | zeek-cut host_name domain | awk '$1 == "vinlap01"'
```

Observed DHCP findings:

| Capture | Finding |
|---|---|
| `smallFlows.pcap` | Host `vinlap01` had domain value `astaro_vineyard` |
| `bigFlows.pcap` | 17 unique hostnames, excluding missing and empty values |
| `bigFlows.pcap` | Domain value `jaalam.net` |

A DHCP domain value is a network setting that can act as a DNS suffix. It does not by itself establish a visited website or Active Directory membership.

```bash
zeek -C -r ftp.pcap local
```

The lab configuration loaded **498 scripts**. `local` loads the local policy and its dependencies; the count depends on the installation. I also practised loading Zeek's built-in FTP brute-force policy, which aggregates failed-login activity rather than simply matching a single response.

## File analysis and intelligence

```bash
zeek -C -r case1.pcap intelligence-demo.zeek
cat intel.log | zeek-cut seen.indicator seen.where | sed -n '2p'
```

The second intelligence finding was `smart-fax.com` at **`HTTP::IN_HOST_HEADER`**: the domain appeared in the HTTP Host header and matched the supplied indicator list. An intelligence match needs contextual validation.

```bash
zeek -C -r case1.pcap hash-demo.zeek
cat files.log | zeek-cut mime_type md5 | grep -F 'application/x-dosexec'
```

The downloaded executable's MD5 was:

```text
cc28e40b46237ab6d5282199ef78c464
```

A hash identifies content for comparison; it does not alone establish maliciousness. Incomplete captured file data can affect the interpretation of hashes.

```bash
zeek -C -r case1.pcap file-extract-demo.zeek
file extract_files/*
```

The extracted objects included ASCII text, an Office compound document and a PE32 Windows executable. The text file contained **`Microsoft NCSI`**.

To connect a file to network activity:

```bash
cat files.log | zeek-cut fuid conn_uids tx_hosts rx_hosts mime_type extracted
```

`fuid` identifies the file; `conn_uids` links it to connections. Following those connection UIDs through `conn.log` and `http.log` helps establish who received the file, from which server and through which request. Encrypted traffic and incomplete captures can limit file visibility and extraction.

## Packages and summary statistics

```bash
zeek -C -r http.pcap zeek-sniffpass
cat notice.log | zeek-cut msg | sort | uniq -c | sort -nr
```

The package produced **3 notices for `BroZeek`** and **2 for `ZeekBro`**. These were cleartext-password submission detections, not evidence of successful account compromise.

```bash
zeek -C -r case2.pcap geoip-conn
cat conn.log | zeek-cut id.orig_h geo.orig.city id.resp_h geo.resp.city
```

The lab GeoIP database associated **`23.77.86.54` with Chicago**. Geolocation is approximate enrichment, not proof of a person's location or malicious activity.

Running `sumstats-counttable.zeek` on `case2.pcap` identified **four distinct HTTP status codes**:

| Code | Meaning |
|---|---|
| 200 | Successful request |
| 301 | Permanent redirect |
| 302 | Temporary redirect |
| 404 | Resource not found |

The same code appearing for several hosts is still one distinct code type.

## What I learned

This lab helped me practise selecting the right log and field, distinguishing unique values from total detections, and linking network and file evidence. My main lesson was to interpret alerts in context: a pattern match, an intelligence indicator or an unfamiliar destination is a starting point for investigation, not a complete conclusion.

These findings come from separate training captures and exercises; they do not represent a single real-world incident.
